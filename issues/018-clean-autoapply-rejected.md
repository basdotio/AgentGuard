# 018 — clean 的"派生态自动档"：实测否决，不要再论证

- **类别**：功能范围（已否决）
- **严重程度**：—
- **状态**：**不规划**。前提经真机实测不成立，2026-08-14。

> **这条 issue 的用途是防止重新发明。** 下面这套推理在纸上非常有说服力，我自己写了
> 一份 400 行的方案，然后一量就废了。如果将来你（或者我）又想到"让 clean 自动清掉
> 那些没人要的东西"，**先读完 §3 的数字，再决定要不要动手。**

## 1. 出发点：一个真实的抱怨

> 「输出太多了，没心情看。」

`clean` 列出的每一样东西都要用户点头，所以清单有多长就得读多长。
`prd-selective-clean.md`(文件未入库) §3.2 已经指出根因：

> **于是 v1 的 A1 档为空，"一键全清"没有可执行内容。**

A1（自动可逆档）为空 ⇒ 100% 的项落到"需要用户决定" ⇒ 阅读量等于发现总数。

## 2. 提出的方案（听起来很对）

那份 PRD 只考察过两个 A1 候选——zombie skill、duplicate 对——**两者都是用户自己写/装的内容**。
对用户自己的内容做判断确实需要用户在场，`ROADMAP.md` B.6 那句"一个悄悄改写它们的工具比一个只
列出来的工具更糟"说的正是这类。

于是想到一条新分界线：**派生态 vs 作者态**。

| | 作者态 | 派生态 |
|---|---|---|
| 谁产生的 | 用户写的 / 装的 | 工具自己生成的缓存、镜像、残留 |
| 谁能判断该不该留 | 只有用户 | 结构本身就能证明 |

对派生态逐项征求同意是**仪式**——用户没有任何判断可以贡献。所以：把派生态放进 A1，
让 `clean` 自动清掉（隔离，可 undo），只打两行摘要。A1 的准入改成三个可判定条件：
Claude Code 证明不加载它 + 不是用户作者的 + 移动可逆。

配套还设计了：非 TTY 一律不写、每个 root 首次确认一次、爆炸半径上限、跳大版本号。

**这套推理没有逻辑错误。它只是前提是假的。**

## 3. 实测（这一节是本文的全部价值）

方法：一份只读的普查脚本，在真机 `~/.claude` 上跑一次。判据：

- **被取代的 plugin 缓存** = `plugins/cache/<市场>/<插件>/<版本>/` 中，没有任何
  `installed_plugins.json` 的 `installPath`（`realpath` 后）落在其中的版本目录
- **已无插件的市场镜像** = `plugins/marketplaces/<市场>/` 中，该市场下已无插件安装
- 断掉的软链 / `.aguard-trash` 存量 / 空 skill 目录 / `.DS_Store` 类

结果（2026-08-14，一个装了 **7 个插件**、用了很久的真实环境）：

| 类别 | 数量 | 体积 |
|---|--:|--:|
| **被取代的 plugin 缓存** | **0** | **0** |
| 已无插件的市场镜像 | 2 | 80.5 KB |
| 断掉的软链 | 1 | — |
| `.aguard-trash` 存量 | 0 | 0 |
| 空 skill 目录 | 1 | — |
| 系统垃圾（`.DS_Store` 等） | 3 | 20 KB |
| **合计** | **6 项** | **约 100 KB** |

### 3.1 决定性的那个 0

**7 个插件，0 个残留的旧版本目录 —— Claude Code 升级时自己把旧版本清了。**

这一条把方案的主要收益直接抹平：本来预期最大的一块（被取代的缓存）**按设计就不会累积**。
其余全部加起来 6 项、100 KB，为它去改一条只读命令的默认行为、加 TTY 判断、加首次确认、
加爆炸半径上限、跳一个大版本号，**投入产出完全不成比例**。

方案自己写了闸门："合计接近 0 → 前提不成立，不要开工第二步。" 按闸门执行。

## 4. 过程中犯的两个错，都值得记

判据在纸上想是不够的。同一个检测项（市场镜像）错了两次：

**错误一：把"没有 `installPath` 指向它"当作镜像已死的判据。**
这对**所有**镜像都成立——`installPath` 一律指向 `plugins/cache/`，从不指向
`plugins/marketplaces/`。照这条规则连在用的市场也会被判死。正确的问法是"这个市场下面
还有插件装着吗"。

**错误二：把 `installed_plugins.json` 的 key 当成市场名。**
key 的真实形状是 **`<插件>@<市场>`**（`claude-mem@thedotmack`、
`superpowers@claude-plugins-official`）。`internal/collect/plugins.go:68` 把这个 key
原样当作 artifact 名，所以扫描报告里才会出现 `plugin:claude-mem@thedotmack (10.5.2)`。
拿 key 直接去比目录名 `thedotmack` 永远匹配不上，于是又一次把所有市场判成死的——
**并且报出"92 MB 可清理"，而真实数字是 80.5 KB。**
那 92 MB 的绝大部分是三个**在用**的镜像（在用的恰好是大的）。

**教训**：一个会告诉用户"这 92 MB 可以删"的诊断脚本，本身就是危险品。
第一版还没有版本号，导致修好之后无法分辨用户跑的是新版还是旧版。
**诊断脚本必须能自证身份。**

### 4.1 另一个纸上没想到的反例

方案 §5.2 曾把市场镜像列为安全的自动档成员。真机上 claude-mem 的 hook 命令是：

```
_R="${CLAUDE_PLUGIN_ROOT}"; [ -z "$_R" ] && _R="$HOME/.claude/plugins/marketplaces/thedotmack/plugin"; …
```

**镜像是它的兜底路径。** 删掉，那条 hook 就静默失效。这正是
`prd-selective-clean.md`(文件未入库) R32（反向引用检查）要防的情形，
而"派生态没人引用所以安全"这个论证在纸上看不出问题。

**结论**：任何未来的自动档成员，移动前都必须过反向引用检查——hook 命令、权限授予、
`installed_plugins.json`、其它 artifact 的引用。可逆 ≠ 依赖关系无损。

## 5. 那么"输出太多"该往哪走

普查同时回答了这个问题：**那些量不是可清理的垃圾。**
环境里几乎没什么可清的，报告却很长 ⇒ 长度来自**发现多**，不是**垃圾多**。

方向是 [017](017-unloaded-tree-files-inflate-counts.md)：`docs/ja-JP/`、`docs/zh-CN/`
的语言副本、`tests/`、`.github/workflows/` 这些**永远不会被 Claude Code 加载**的文件在
照样打分、照样进报告。那条路砍的是**发现列表本身**，不碰写权限，风险小一个量级。

## 6. 什么情况下值得重新考虑

- Claude Code 改变行为，升级时**不再**清理旧版本目录（`plugins/cache` 开始堆积）
- `.aguard-trash` 因为 `clean --apply` 被常用而增长到有意义的量级
- 出现新的、体量大的派生态（比如某种本地索引 / 向量库缓存）

**重新考虑的第一步仍然是数一数，不是写代码。**
