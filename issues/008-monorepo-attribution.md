# 008 — 大型 monorepo 按单一产物打分，发现无法归因

- **类别**：归因粒度
- **严重程度**：低（不影响正确性，影响可用性）
- **状态**：**部分修复**（修复方向 3 已做，见下方"实测与决定"）；方向 1（拆产物）**主动放弃**

## 问题描述

一个"monorepo 即一个 skill"的大型工具集（例如某些大型工具集仓库）被扫描为**一个产物**。后果：

- 它的所有 finding 都挂在**同一个名字**下，看不出是哪个子目录/子命令的问题；
- 整棵树只有**一个分数**，一个子模块的严重问题会被整体平均稀释，或反过来把
  整个工具集拉黑。

## 已解决的相邻问题（不要混淆）

- **速度**：A.3 并发扫描已解决（有界 worker pool，按索引写回，输出与串行一致）。
- **噪音**：A.4 `.aguardignore` 基线 + 声誉允许列表已解决（可信工具的示例不再淹没报告）。

剩下的**只有归因**这一项。

## 出处

- ROADMAP "Known limitations"：`Large monorepo-as-one-skill (e.g. a large toolkit repo) is scanned as
  ONE artifact … The attribution one remains.`

## 修复方向

1. **子产物拆分**：当一棵树包含多个可独立识别的单元（多个 `SKILL.md`、多个命令目录）时，
   拆成父产物 + 子产物，finding 归到子产物，分数在父层聚合展示。
2. **与规范哈希的冲突要先想清楚**：哈希是声誉库的键。拆分后是"父树一个哈希"还是
   "每个子产物各自一个哈希"？前者简单但子产物无法单独允许/阻止；后者更细但会让
   声誉库条目数量膨胀，且父树任何改动都不再影响子哈希。建议：**父哈希保持不变**
   （声誉键不动），子产物只用于**报告归因**，不进声誉库。这样能在不动核心契约的
   前提下拿到全部可用性收益。
3. 报告层面即使不拆产物，也可以先做**按文件路径分组**的展示改进，成本远低于第 1 项。

## 实测与决定（真机扫描之后）

先量，再改。在一台真实的 `~/.claude` 上跑完之后，本条 issue 的两个后果一个被高估、
一个被低估：

**"看不出是哪个子目录的问题"被高估了。** 303 条 finding 折叠成 **40 个
(产物, 规则) 组**——终端报告 40 行，是可读的。聚合本来就在做归因的大部分工作。

**真正丢失的信息是"有多宽"。** 其中一组 `EXFIL-001` 有 56 条、跨 **28 个文件**，
而报告只显示 3 条 evidence。`×56` 单看和"一个文件命中 56 次"完全一样，但两者要求
的反应正好相反：改一个文件，还是不信任整棵树。

所以做了方向 3，但落点不是"按路径分组"，而是**把宽度本身变成一个数**：

- `Group.Files` = 该组涉及的**去重文件数**（每条 evidence 的每条腿都算，因为
  `EXFIL-003` 这类结构性 finding 的腿分散在多个文件里，它们都受影响）；
- 计数行变成 `×56 in 28 files`（只有一个文件时不加这半句，`in 1 files` 是废话）；
- evidence 之后补一行 `… and 25 more file(s)`。**这一行比列出来更重要**：没有它，
  上面 3 条路径读起来就是全集，改完那 3 个的人会以为这组关掉了。
- 两个渲染器共用 `Group.MoreFiles()`，因为 HTML 模板算不出这个差值，而"终端报告和
  HTML 永不漂移"是既有约束。

**方向 1（拆产物）主动放弃，理由是实测的：**分数是按产物**平均**的。把一棵树拆成
N 个子产物之后，干净的子产物会把脏的那个平均掉——在另一条分支上实测过同一棵树
**86 → 97**。也就是说拆分不是"更细的归因"，是**虚高**。归因的收益已经由聚合 +
`Files` 拿到了，代价却要动分数语义和声誉哈希键。不做。

方向 2（哈希键怎么处理）随方向 1 一并搁置——不拆就不存在这个冲突。
