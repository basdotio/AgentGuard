# 015 — manifest 是完整性可验证，不是防篡改

| 项 | 值 |
|----|----|
| 类别 | 威胁模型边界（非缺陷） |
| 严重程度 | 中（隐蔽性已缓解；密码学层面的边界无法在单机工具内消除） |
| 状态 | 部分修复（已记录为边界） |

## 起因：一个 013 审计没抓到的绕过

`Undo` 的身份校验是"trash 里内容的哈希 == manifest 行里记的哈希"。审计的
`TestUndo_RefusesSwappedContent` 测的是**改内容不改 hash**。**两个一起改**则通过：

```
1. 隔离一个无害的 skill
2. 把 trash 里的内容换成 curl … | bash
3. 把 manifest 那行的 hash 字段也改成新内容的哈希
→ clean --undo last  →  "restored dead → skills/dead"
→ 恢复出来的是 payload
```

根因是一个**逻辑循环**：用一个攻击者能写的文件里的值，去验证攻击者能写的另一处内容。

## 这个绕过的真实价值：隐蔽，而不是权限

能写 `~/.claude/.aguard-trash/` 的东西**本来就能写 `~/.claude/skills/`**——它可以直接装一个
恶意 skill，不需要绕道。所以这个攻击**不给攻击者任何新权限**，它给的是一个**更隐蔽的投递
方式**：payload 以"用户主动恢复自己的文件"的形式进来，用户认为那是自己原来的东西。

**所以对策也应该针对隐蔽性，而不是去加更强的校验。**

## 已缓解：恢复前预览（`internal/clean/preview.go`）

每一项恢复之前（dry-run 也一样）打印将要放回去的内容摘要，并**跑一遍静态引擎**：

```
restoring dead ← …/.aguard-trash/dead
      directory, 1 file(s), 68 B, sha256:0b9d9c5c98526b13…
      │ SKILL.md
      ⚠ scan of the quarantined copy: 1 high
      ⚠   EXEC-001 curl piped to shell
restored dead → …/skills/dead
```

跑规则而不是只显示头几行，是因为**实测下 payload 在 SKILL.md 的正文里**——列文件名只看到
`SKILL.md`，显示头三行只看到 frontmatter，两者都看不到 `curl … | bash`。规则能看到。

用的是 `aguard check <path>` 同一条流水线，所以预览不可能和用户手工审计隔离副本的结果不一致。
预览失败时**吞掉错误**：一个跑不起来的预览不能阻止恢复，因为拒绝恢复不会让谁更安全，
只会确保 manifest 本来要防止的那次丢失真的发生。

## 已缓解：哈希链（`Record.Prev`）

每行带上一行的 SHA-256，读时重算验证。**能测到什么、不能测到什么都是实测的**，并且用
**反向断言**固化在 `TestChain_CannotDetectEndOfFileTampering` 里：

| 情形 | 是否检测到 | 靠什么 |
|---|---|---|
| 删掉**中间**某行 | ✅ | 后一行的 `prev` 不匹配 |
| 改写**中间**某行 | ✅ | 同上 |
| 半截/不可读的行 | ✅ | 解析失败 |
| 删掉**最后**一行 | ✅ | **不是靠链**——写前记录成对，缺 `done` 会留下未确认的 `intended` |
| 改写**最后**一行 | ❌ | 后面没有行来锚定它 |
| **完全清空**文件 | ❌ | 没有行就没有链可验 |

最后两行是**锚点在被保护数据内部**的固有性质，不是实现疏忽。

因此对外的表述是 **integrity（完整性可验证）**，README 里写的也是这个词。**不能写
"防篡改"（tamper-proof）**——那会是一个假保证，而假保证比没保证更糟。

断链**只警告、不拒绝恢复**：文件已经不在 `skills/` 了，拒绝只会确保丢失而不是防止丢失。
恢复本身的安全由五重校验保证（每一条都从文件系统重新推导），链的职责是**告知历史丢失或被
编辑过**——那是用户否则看不到的事——并让他带着怀疑去读接下来的预览。

旧格式（无 `prev`）的行报告为"无法验证"但**仍然可恢复**：让一次升级变成一个批次不可恢复的
原因，本身就是数据丢失，比它要关的缺口更糟。

## 要真正闭合，需要外部锚点——以及为什么这个交易不明显值得

链头必须放在攻击者碰不到的地方，而每个选项都要付掉这个工具被选择的某个性质：

| 方案 | 代价 |
|---|---|
| root 内的第二个文件 | 同样可写，等于没做 |
| root 之外的文件 | 违反 clean「只在 root 内动」的自有原则 |
| 系统 keyring | 需要平台特定代码，破坏 `CGO_ENABLED=0` 单二进制 |
| Ed25519 签名 | 私钥放哪？单机工具没有可信存储 |
| 链上锚定（D.12） | 需要网络，破坏「完全离线」 |

而收益是**堵住一个不提供新权限的隐蔽通道**——隐蔽性那一半已经由预览处理了。

**结论：现在不做。** 如果哪天 D.12（链上认证）落地，链头天然有了一个外部锚点，那时这条
边界会自己消失，届时应翻转 `TestChain_CannotDetectEndOfFileTampering` 的反向断言。
