## 0. 定位：开源产品为主（已定，2026-09-13）

曾经的岔路是：**争夺用户的开源产品，还是证明服务的基础设施？** 已定为前者。

下表保留备查 —— 它解释了为什么阶段 2/3 的顺序是现在这样，也说明"辅"的那一列
（`verify`、BOM）没有被删除，只是后置：

| | 如果是**开源产品** | 如果是**证明基础设施** |
|---|---|---|
| 成功指标 | star、安装量、被清单收录、外部贡献 | 分数可被第三方复算、制品事实可锚定 |
| 平台广度 | 关键（我们 1 个 harness，对手 13 个） | 几乎不重要 |
| 名字撞车 | 严重问题 | 次要问题 |
| 规则数/检出率 | 要能对比 | 要能复现，不要最高 |
| 最该先做 | 公开、清单、截图、广度 | `verify`、BOM、报告链 |
| 最大对手 | NVIDIA / Snyk / Cisco / Tencent | 没有对手，只有标准 |

**为什么这个岔路真的存在**：org 是 `basdotio`（BNB Attestation Service），`ROADMAP.md` 里
D.12 是 ERC-8004 上链证明，`Overall` 被刻意冻结成"可字节级复算"就是为了它，`internal/sink`
留着云端信誉的接口 —— 全部指向右列。而当时的规划文档整篇按左列写。**两边的证据都在，所以
它必须被显式决定，而不是靠默认。**

定为左列之后：平台广度的配置层回到正式排期，名字撞车升为必须解决，BOM 与报告链后置但不删。
排期见 [plan.zh-CN.md](plan.zh-CN.md)。

## 1. 当前问题

按"会不会让前面的努力全部作废"排序，不按修复难度。

### 问题一：工具的核心承诺目前不成立

这个扫描器的全部价值建立在一句话上：**我看了，这是我看到的，这是我没看到的。**

审计确认它有**四种**静默失败方式 —— 一条 `chmod`、29 个字节、一个 FIFO，都能让它输出
`100/100 · ✅ No risk findings`，而被扫内容完好无损。其中一条还会顺手在闸门里记一条"已信任"。

**这不是缺陷列表，是资产为负。** 一个把"说出自己不知道什么"当作立身之本的工具，
被发现有四种不声不响地什么都不知道的方式 —— 在这件事修好之前，任何数字、任何定位、任何分发
都是在给一个可被静默的扫描器背书。

### 问题二：赛道已被占，而且我们不在头部

| | ★ | 扫什么 |
|---|---|---|
| NVIDIA/SkillSpector | 16,927 | 目标制品 |
| Tencent/AI-Infra-Guard | 6,231 | 平台 |
| Snyk/agent-scan | 3,033 | **已装环境，13 个 harness** |
| Cisco/skill-scanner | 2,513 | 目标制品 |
| 我们 | 私有 | **已装环境，1 个 harness** |

计划里那四格"独占"（供应链制品审计 / 已装环境 / 可复算分数 / 修复）**每一格都有人做到了**，
其中两格有人做得更宽或打平。"没人做过这件事"这个前提已经不存在。

### 问题三：没有任何可引用的数字，而同行有

同行不是"都带语料"，是**已经把数字发出来了**，包括难看的那组 —— Cisco 主动公布自己在锁定划分上
只有 7.75% recall 并写明"未通过晋级门槛"。

同时有公开研究报告称某一类打包手法能以 **>90% 成功率绕过全部 8 个受测扫描器**。
我们的形状检查正对着这一类，**但没有任何数字证明拦得住**。

### 问题四：身份不清

"AgentGuard" 这个名字已被一个同定位、活跃、star 高一个量级的项目占据，另有一个项目的**仓库名
精确撞车**，加上十几个同名项目。搜索这个名字找不到我们。

同时产品的可见性是个半成品：分发仓库已公开但没有 LICENSE、没有描述、没有主题词，
release 落后源码两个版本导致插件让用户升级而升不上去；源码仍然私有。

### 问题五：维护面已经超过人力（没人提过的那条）

现在要长期维护的面：10 个维度 72 条规则 · 加载期闸门 · 可逆隔离 · 下载目录流水线 ·
LLM judge · 信誉库（含每周自动续期）· npm 五个包 · Claude Code 插件 · 双仓库分发 ·
桌面版三套未文档化布局 · 28 条实测得来的权限逃逸表。

对手背后是 NVIDIA、Cisco、Snyk、Tencent 的工程团队。**广度竞赛在算术上就输。**
而每一个新方向都会再加一个必须长期维护的面 —— 这是本文档所有取舍的真正约束。

## 2. 框架：资产是克制，不是覆盖

这个仓库真正与众不同的东西，不是它扫了什么，而是它**拒绝做什么**：

| 承诺 | 代价（也就是为什么别人不做） |
|---|---|
| 绝不执行被扫内容 | 拿不到 MCP server 的真实工具清单 |
| 绝不外连 | 没有云端威胁情报、没有共享黑名单 |
| 分数可离线复算，LLM 只能单向升级 | 放弃了"让模型把分数调好看"这个选项 |
| 批准绑定字节而非名字 | 用户每次内容变化都要重新确认 |
| ~~任何遗漏都要出声~~ | **2026-09-14 更正：这条不再是差异点，见下** |

**这些是信任属性，不是功能。** 功能可以被一个十几人团队一周抄完；信任属性抄不了 ——
因为它们要求你**主动放弃能力**。

这个框架有一条可验证的支撑：覆盖面最宽的那个竞品，README 里逐字写着它会**执行**被扫的 MCP 配置
（CI 里还是**强制**的），并把 **skill 正文**上传到自家 API（脱敏是 best-effort，且不可关闭 ——
关掉等于工具失去全部检测能力，因为它 15 条 risk 全在云端判）。也就是说这条赛道上"更宽"和
"更克制"目前是互斥的，而没有人站在克制那一端。

### ⚠️ 更正：覆盖披露不是我们独有的（2026-09-14）

`NVIDIA/SkillSpector`（17,140★）**已经做到了，而且比我们细**：52 个白名单化的原因码、
5 种结果类型、终端无条件印 "Inspection Completeness" 表（含 Coverage % 与 Entirely
uninspected）、四种输出格式一致且有参数化测试钉住。更激进的是它的 `AE1` 是一条 **HIGH 计分
规则**（引用了没能完整检查的文件），而我们的 `COV-000` 是 dim 0 不计分。它还有 fail-closed：
扫描不完整时 recommendation 从 `SAFE` 降为 `CAUTION`，分数不动。

`Tencent` 也独立走到了同一条（PR #623：「空输出的扫描被评分为满分形成假阴性」）。

**所以对外材料里不能再把"遗漏必出声"写成我们独有的。** 证据与逐条核实见
audit-log.zh-CN.md(已归档,不在本仓库) 条目 4。

**剩下真正独有的两条**（四家竞品全无）：
1. **LLM 只能单向升级。** NVIDIA 的模型可以发明未文档化的规则 ID、可以自判 CRITICAL，
   输出里分不出静态发现与模型发现；Snyk/Tencent 的 LLM 是唯一判决者，**一次成功注入的收益是
   正的**。我们的 `min()` 结构让它为负。
2. **加载期闸门 + 字节绑定批准。** NVIDIA 靠 agent 自愿调用 MCP 工具，Snyk 把 hook 事件转发
   云端判决，Tencent 没有这个概念。

外加一条**组合独有**：已装环境 + 确定性分数 + 可离线复算 + 可逆隔离。

还有独立证据说明这条路走对了：一个企业 AppSec 团队包了 Cisco 的扫描器，**因为 LLM 严重度逐次
跑不稳定，把自动拒绝的权力只留给确定性发现** —— 这是我们不变量 #4 的一半被不知道我们存在的人
重新发明了一次（但他们额外加了一道 **demote-only** 的 LLM 裁决，方向与我们相反）。
另有两个零流量项目各自独立收敛到"无证据的发现永不影响分数 + 字节稳定输出 + 零依赖"。

**所以方向不是"变成更全的扫描器"，是"变成可被审计的审计器"。**

这个框架同时解释了为什么问题一是生死问题：那四种静默失败**恰好击穿的就是这唯一的资产**。

## 3. 方向：四个阶段，每个阶段有门槛

**不排具体日期。** 每个阶段有一条门槛，没过就不进下一阶段 —— 因为后一阶段的产出会以前一阶段
为前提，顺序错了要重做。

### 阶段 0 · 止血

修掉那四种静默失败，以及自己身上那条"凭据内容出网"的口子（它和我们要批评竞品的形状完全一样，
不修就说不出口）。补上发布缺口。

**门槛：扫描器不能被被扫对象说服去保持沉默。** 具体判据是每种静默路径都有一条反向断言测试钉住。

> 这一阶段不产出任何对外可见的东西。**它的价值是让后面三个阶段不是在撒谎。**

### 阶段 1 · 证明

**先接别人的对抗性 harness，不要自建语料。** 已经存在一个 MIT 许可、默认盲测、答案放在扫描器
看不到的地方、且已经为四个竞品写好适配器的 benchmark。接进去就有第一组数字，成本比自建低一个
量级。而它针对的规避手法（填充、同形字、字节码、归档间接、判官操纵）正是我们已经专门做过的那些
—— 有机会在这个 harness 上压过 star 数高一个量级的对手。

然后才是自建语料：**harness 的结果会告诉你缺哪一类样本**，反过来先收样本一定要重标。

同期把报告做成自证可复现的（规则集版本 + 输入摘要 + 一个离线重算命令）。这是分数可信的最小
技术条件，也是上链证明的真正前置。

**发数字的纪律照 Cisco 学：难看的那组也发，并写明它为什么难看。** 这正好是这个仓库已有的披露
纪律用在自己身上。

**门槛：能说出一句带出处、带 n、可被第三方复算的成绩。** 不是"检出率 X%"。

### 阶段 2 · 定位

有了阶段 1 的数字，才有东西可定位。三件事同时做：

- **收窄战线，公开承认不做什么。** 见 §4。
- **解决名字。** 这是决策不是工程，但拖着会让阶段 1 的数字找不到读者。
- **把可见性补齐**：源码是否开放、双仓库怎么办、许可与描述、清单收录。
  优先低门槛的清单，而不是那个由利益相关者把持收录的。

**门槛：一句站得住的定位句，且它不含"首个""唯一""最"。**

参考形状："审的是已经装在你机器上的东西，从不执行它、从不上传它，给出的分数你可以离线重算。"
这句话今天就是真的，且据我们检索所及没有第二个工具能整句说出来 —— 但**这是一句关于组合的主张，
不是关于任何单项的**，措辞上不能滑到"独占"。

### 阶段 3 · 扩张（只有前三阶段都过了才有意义）

三个候选。产品定位下的顺序（2026-09-13 调整）：

1. **平台广度，配置层先** —— `.cursor` / `.codex` / `.gemini` 的 MCP 与 hooks 配置。
   评分维度不变。**制品层（rules / AGENTS.md）仍是条件性的**：只在某个平台有真实用户反馈后
   启动，因为每个平台要一套加载语义实测，是维护面最重的一项。
   **没跑过测试的平台不进 README。**
2. **报告链与归属** —— 让报告能证明未被事后修改，并回答"这台机器上环境变了什么"。
   注意这是这个工具第一次要长期保存自己的产出，重的地方在存储与迁移不在哈希。
   **不要碰签名**，除非能回答密钥放哪、谁验、丢了怎么办。
3. **制品事实视图（BOM）** —— 不改内部模型，只加一个视图和一份格式说明。
   作为"辅"保留，等消费者出现。

## 4. 明确收窄和放弃

**这一节和方向同等重要。** 维护面已经过载（问题五），所以每加一样东西都要减一样。

| 项 | 判断 | 理由 |
|---|---|---|
| **规则数竞赛** | **彻底放弃** | 口径不同，且规则数是所有对比项里信息量最低的一个 —— 它既不说明检出率也不说明误报率。为了一个数字去拆规则，是把唯一有意义的指标换成一个无意义的 |
| **平台广度** | **配置层正式排入阶段 3；制品层条件性**（2026-09-13 按产品定位调整） | 对手 13 个 harness，我们 1 个，算术上追不上全部，但配置层（MCP/hooks）跨平台高度相似、维护面可控。制品层每加一个平台要一套加载语义实测 + 一个永久维护面，**只有当某个平台的用户真的来问时才加** |
| **扫 agent 应用源码** | **不做** | 制品不同、用户不同、生命周期不同。补这块等于开第二个产品，且正好是对手已经拿到最多 star 的那个 |
| **框架级工作流映射** | **不做** | 要解析别人的框架代码。我们的产出本身就是那张图，只是从配置来 —— 需要图就做 BOM 视图 |
| **运行时监控** | **明确不做，并写进文档** | 我们最硬的不变量是"绝不执行被扫内容"，运行时监控要求的恰好相反。正确动作是把边界**写出来**并指向做这件事的工具 |
| **AST 检测** | **推迟到阶段 1 之后** | 纯 Go parser 是大依赖，tree-sitter 要 CGO，两者都动"单静态二进制 + 三个依赖"这条线。而正则精度是不是真问题，只有 benchmark 的"错误响"那一列能回答。现在做是为一个未经测量的假设付大额依赖成本 |
| **签名 / 上链** | **推迟到可离线复算之后** | 顺序是反的：先让第三方能离线复算并验证，再谈把摘要锚上去 |
| **合规声明** | **不做** | "合规"是关于一个组织的声明，不是关于一次扫描的。最多能说某项输出**服务于**某条记录义务 |
| **第四个依赖** | **默认不加** | 每个依赖都要照现有标准论证一遍，并且必须看它的 go 指令 |
| **加载期门禁默认开** | **驳回**（2026-09-13 外部建议） | 见下 |

### 为什么"门禁默认开"是驳回而不是推迟

有外部建议说：装了新 skill 时跳出来问一句，是产品对普通用户唯一可感知的价值，应该默认装上
而不是询问。三条理由驳回：

1. **它与另一份外部反馈的结论正面冲突，而那份的论证无法反驳。** 第三方误报核验指出：按当前
   误报率，门禁装上后每次加载 skill 都可能弹窗，人会很快养成无脑点"同意"的习惯 —— 到那一步
   它**比不装更危险**：用户付出了全部摩擦成本，换来一个已经失效的判断力。这正是本仓库自己的
   判据（"被忽略的告警等于没有告警"）。
2. **`CLAUDE.md` 已经把它写成设计原则**：一个"帮你审 hook"的插件顺手给你装一个 hook，
   正是它教用户提防的形状。所以 `hook install` 保持显式、且先 `--dry-run` 给人看。
3. **顺序是反的。** 先压误报，再谈默认。

可接受的形态是 setup 流程里**一步醒目的、一键的、解释清楚的选项**，不是静默默认。

### 为什么这四块不做（逐条论证）

**扫 agent 应用源码。** 制品不同、用户不同、生命周期不同：他们审"开发中的 agent"，用户是
**写** agent 的人；我们审"已安装的环境"，用户是**用** agent 的人。补这一块等于开第二个产品，
而且正好是他们已经拿到最多 star 的那个。往他们的格里挤，是把唯一还站得住的差异换成一场必输的
追赶。

**框架级工作流映射。** 要解析 LangGraph / CrewAI 的 Python 才能画图，同上。而且我们的产出
**本身就是那张图**，只是从配置来而不是从代码来 —— 需要图的时候做 BOM 视图，不是去读别人的框架。

**运行时监控 / replay / rollback。** 另一层。我们最硬的不变量是"绝不执行被扫描内容"，
运行时监控要求的恰好相反。正确动作是把边界**写出来**，而不是去填。

**把规则数追平。** 口径不同，而且规则数是所有对比项里信息量最低的一个：它不说明检出率，
也不说明误报率。真正的答案是语料上的精确率/召回率。**为了一个数字去拆规则，是把唯一有意义的
指标换成一个无意义的。**

**贯穿所有取舍的一条纪律**：这个工具整体建在披露上 —— 报告未覆盖的、报告被抑制的、
标注不可确证的。**在"合规""签名""首个/唯一"这三类词上越界一次，前面所有纪律一起作废。**
这不是谨慎，这是唯一资产的保护条款。

## 5. 两个风险

**风险一：维护面超过人力。** 这是最可能的死法，而且不会有征兆 —— 表现是规则停止更新、
信誉库续期任务长期红着、桌面版换了布局没人发现、发布缺口再出现一次。
**对策是收窄（§4），不是更努力。** 任何新方向先问："这会不会再加一个必须永久维护的面？"

**风险二：窗口在关，但关的方式和计划想的不一样。** 计划担心的是"被别人抢先做这件事"——
那已经发生了，且不可逆。真正在关的窗口是**克制那一端还空着**：目前"更宽"和"更克制"互斥，
但这只是当前状态。哪天一个大厂决定发一个"本地、不执行、不外连"的版本，唯一的资产就没了。
**对策是把克制做成可验证的（阶段 0 + 1），而不是做得更宽。**

---

## 6. 一页总结

**问题**：工具的核心承诺（我看了，这是我看到的）目前有四种静默失败方式；赛道已被 star 高一到两个
量级的对手占据且我们覆盖最窄；没有任何可引用的数字；名字被占；维护面超过人力。

**框架**：资产不是覆盖面，是**可被验证的克制** —— 不执行、不外连、可离线复算、批准绑字节、
遗漏必出声。这些抄不了，因为它们要求主动放弃能力。目前这条赛道上"更宽"和"更克制"互斥，
而克制那一端空着。

**方向**：止血（让沉默不可能）→ 证明（先接别人的盲测 harness，再自建语料）→ 定位（收窄 + 命名 +
可见性）→ 扩张（配置层广度先，报告链，BOM 后置）。每一步有门槛，没过不进下一步。

**放弃**：规则数、平台广度竞赛、agent 源码、框架映射、运行时、AST（暂）、签名（暂）、合规措辞。

**最大风险**：不是被追上，是维护面压垮人力 —— 所以收窄本身就是方向的一部分。
