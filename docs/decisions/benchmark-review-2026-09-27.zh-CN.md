## 2. 逐实验结论

### 2.1 aguard 静态:精度站住了,召回没动

**三天八条改动各自贡献了什么**(同一批 3,539 个样本上修前修后 diff):

| 改动 | 恶意 | 良性误报 |
|---|---|---|
| P-010 凭证腿(`env \|`、`printenv \|`、`.env`/`.netrc` 读取) | +11 | 0 |
| P-011 / P-015 测量基础设施(127 个 MCP 源码从"不发判定"改为真交给 `check`) | +14(**量法**,不是规则) | 0 |
| P-012 SKILL.md 里的裸 URL 是文档不是请求 | 0 | **−43** |
| P-013 `.mcp.json` 给自家 `url` 加鉴权头不是外泄链 | 0 | **−29** |
| P-016 配置面四条规则 | +2 | 0 |

真正加检测的只有 P-010 和 P-016。误报像一个漏点集中的水龙头(首轮 219 里 144 是同一条规则),拧一次好大半;
漏检像屋顶几十处小缝,每处几滴,补一处看不出来——**213 个漏检里没有一条规则能翻回超过 10 个**。

- **误报按来源,首轮 → 现在**:真实 SKILL.md(n=1996)6.7% → 4.7%(93);真实 settings/.mcp.json(n=387)
  9.0% → **2.1%**(8);skillet-wild(n=474)5.5% → 4.9%(23);真实 MCP 工具目录(n=353)6.2% → 5.7%(20)。
- **剩下 147 个误报按规则**(按规则计,一个样本可命中多条,故行合计 151):`EXFIL-001` **71**(`Bearer ${TOKEN}` 加一条真实的 `curl https://api.xxx`,凭证发给它自己的服务
  → 第 4 步目的地一致性)· `EXEC-001` 21(安装文档里的 `curl … | sh`,**不动**,agent 真会照着跑)· `MCP-001` 20
  (真实工具目录里"读取用户配置"这类合法描述 → 单独调窄)· `FS-001`/`FS-003` 24(读 ssh 目录的示例、`rm -rf` 出现在
  权限白名单字符串里,**未分析**)· 其余 15(`EXFIL-003`、`PERM-005`、`SUP-006`、`INJ-001`)。
- **213 个漏检按"什么能修它"分层**:Cisco 服务端应用漏洞 72(**出界**)· 剩余朴素形状 42(十来种,每种 1–8,**规则还能碰**)·
  纯自然语言 38(归判官)· Cisco 子进程调用 31(和良性代码一模一样,归 AST)· 编码或跨文件拆分 16(**规则还能碰**,还原后再扫)·
  Cisco 停在 low 10(其中 5 个反弹 shell,**规则还能碰**)· 二进制容器 4(不做)。
  三层"规则还能碰"合计 68 个:**静态在这批语料上的天花板约 155/300 = 52%**,这是本文自己按 artifact 的分层加出来的数,不是实测。
- **按来源召回**:skillcraft-audit 30/42(71%)· skillsgoat 17/65(26%)· datadog 真实恶意 8/22 · cisco 14/127(11%,
  按定位能碰到的上限约 21)· hooks/permission/connector 复刻 8/16(P-016 后 hooks 4/5、permission 2/6、connector 2/5)。
- **"Python 执行提级"已撤**:`EXEC-004` 提 high 能翻回 24 个,代价 19 个良性,违反"任何一步不得让误报高于上一步"。
- **hard negative 4/19 三天没变**:3 个是"遇到注入要拒绝"这种防御性文字被当成注入(issue 011 记录了失败修法)。
  19 个里 2 个是我们自己的 fixture,发布时要给 19 和 17 两个分母。
- **来源间极差 60 点**:变远是因为 Cisco 列第一次进了分母,不是变差。

### 2.2 cc-audit:另一种取舍,而且差集说清了它多抓的代价是什么

| 300 个恶意 | cc-audit 抓到 | cc-audit 漏 |
|---|---|---|
| aguard 抓到 | 82 | **5** |
| aguard 漏 | **103** | 110 |

- **它多抓的 103 个里 61 个是 Cisco 服务端代码**:28 个 aguard 零发现(SQL 注入、SSTI 那批,按定位不做);
  **33 个 aguard 报了 medium 或 low 的子进程、eval、base64,cc-audit 直接判 fail**。这正是我们量过、因为要多误报 19 个良性
  而否掉的那一步。**不是它会我们不会,是它付了我们不愿付的价**——那 1,066 个只有它报的良性就是这一步的账单。
- **42 个非 Cisco**,按我们计划里的类别对上号:反弹 shell 3(W-027)· 编码和拆分 7(base64 包裹 ×4、跨文件拆分、引号拼接、
  零宽和 bidi 字符;它对"有编码"本身判 fail,我们的 `OBF-001` 是 medium)· 远程取指令和信标 5(`curl URL?host=$(hostname)`、
  写 git hook、写 shellrc)· 纯自然语言 12("不要告诉用户"、"把 archive@ 加进 BCC";它用关键词规则抓,代价在良性侧)·
  配置面 6(`bypassPermissions`、`enableAllProjectMcpServers`——34/387 良性在用,不做;工具说明投毒 ×2)· 其他 9
  (env 遍历提级、`sudo pip`、`--perm full_access`)。
- **我们独有的 5 个全是结构化检查**:连接器工具清单哈希变化(rug pull)、随包 `.pyc`、按时间或环境门控的行为、跨文件引用的载荷、
  邮件 BCC 外发。cc-audit 纯逐行,这些它看不见。**我们的差异化不在召回,在"看结构、说得清是哪类"**。
- **良性侧**:两家都报 125,只它报 1,066,只我们报 **22**——其中 19 个是 `EXFIL-001`。差集又一次指向第 4 步目的地一致性。
- 它在每一个维度上召回都高于我们(execution 56% vs 18%、injection 57% vs 36%),同时良性池误标是我们的 6–12 倍,硬否定 14/19。
  **attribution 是唯一我们明确赢且区间不重叠的一轴**(59% [48,68] vs 39% [32,46])。
- **「cc-audit 覆盖窄」这句话作废**——它的自述面比我们宽,这句话在 2026-09 的竞品调研里还成立过;那份调研已随内部文档归档,对外叙事按本文改。
- 它的 SARIF **不填 `artifacts`**,对空目录也报 `passed: true / 0/100 safe`:输出里没有任何东西能分开"读了没找到"和"根本没读"。
  这正是我们不变量 #5 和 tripwire 存在的理由。阈值没对齐,公平的比法是同一误报率下比召回,现在只有两个点。

### 2.3 skill-scanner:最像我们的对照物,而它只读一个面

- **strict 档要 `SKILL.md`**:mcp 0/487、connector 1/126、hooks 1/196、permission 2/178 被读。
  897 个 no-verdict 全是 `unsupported-input` 带 loader 原话。**它在四个面上的零是拒绝不是漏**——
  记成漏它是 9%,记成过它有 900 个样本的完美误报率,两个都不是真数。
- **它没有批自己的卷子,它连卷子都没打开**:`cisco-mcp-scanner-evals` 127/127 全是 `.mcp.json`,全被拒。
  第二个分母(剔除该来源)在 3,412 个共同样本上**零判决差异**。
- 在它读的 skills 面上:skillsgoat 11% [5,21]、skillcraft-audit 10% [4,22];良性 skillet-wild 6%、skillmd-138k 2%。
  **三家里最克制,召回也最低**。
- **tripwire 两次拦对**:第一遍 mcp 0/130 要声明;第二遍我声明过头判 `stale-declaration`。P-015 建的这道闸门第一次在真实数据上触发。
- `deeply-nested` **崩了**(`OSError: [Errno 63] File name too long` 死在 `pathlib.stat`);`marshal.load()` 那条路在本 venv(3.12)上
  没被走到(3.14 的 `.pyc` magic 不匹配),它以 HIGH 披露"无法验证的字节码"——好行为,但换 3.14 运行时会走到。
- **exit 1 有两个意思**(闸门响 / 目录不存在 / SkillLoadError 同码),adapter 只看它印了什么。
- `dimension_map` 按提升度**算不出来**:能算的只有 23 个样本。五条按名字、逐条标"未测",证据等级低于 P-017。
- 已交付为 P-022(原 019,撞上游同号后推改号),PR #23 待合入;语料仓 `taxonomy` 已推(`4f964622`)。

## 3. 横向结论

1. **精度是我们唯一站得住的位置,而且是三家里最好的。** 误报 4.6% 对 37%,硬否定 4/19 对 14/19,
   attribution 59% 对 39%(区间不重叠)。`direction` 说"资产是克制,不是覆盖"——数据第一次撑住了这句话。

2. **静态召回是三家里最低的,规则层面已接近它在这批语料上的天花板(约 52%)。** 三天八条改动召回只动了 2 个;
   213 个漏检没有一条规则能翻回超过 10 个。**差集把这一点钉死了**:cc-audit 多抓的 103 个里,33 个是我们看见了但停在
   medium/low 的子进程、eval、base64——它靠"见到就 fail"拿走这 33 个,账单是 1,066 个良性。**再靠加正则或提级涨召回,
   会以精度为代价**,而精度是唯一的资产。

3. **我们独有的东西是结构,不是行。** aguard 独抓的 5 个全是结构化检查(清单哈希变化、随包 `.pyc`、时间/环境门控、跨文件载荷、BCC);
   attribution 59% 对 39% 是同一件事的另一面。**这决定了下一步的形态:做机制(还原、目的地、结构),不做规则条数。**

4. **召回缺口是结构性的三块**,每块对应不同工具:
   - 服务器端应用漏洞(Cisco 72 + 二进制 4)—— **出界**;
   - 语义类 38 —— **判官的主场**,nvidia 5/5 和 LLM-003 零良性升级是证据;
   - 朴素形状 42 + 编码/拆分 16 + Cisco low 10 —— **静态该抓而没抓**,是接下来三步的全部内容。

5. **判官的位置已经清楚:第二层,叠加,delta 单报,权限只能往上。** 78% 对 42% 说明有效;+0.4% 说明代价可控;
   `LLM-009` 的教训说明**卫生类规则不能进闸门**(spec §5.2.1"规则级资格")。但它还没过方差、全量良性、成本三关;
   而且 skill-safety-bench 上 5 个"看见了但没落地"的发现,说明**证据落地那道门本身也要量**。

6. **测量台自己交出了四个发现**,每个都改变"能说什么":tripwire 在真实数据上两次拦对;`corpus score` 对不报维度的工具印 `0%`
   与"每类都说错"无法区分(缺陷未修);仓库里**没有容器执行路径**,三家的 `uploads_samples` 都只能写 NOT MEASURED;
   一个只在预计会赢时才跑的 benchmark 不是 benchmark——cc-audit 那列我们输了召回,照样入库。

## 5. 方向

### 5.1 定位不用改,数据第一次撑住了它

`direction` 2026-09-13 定的是"变成可被审计的审计器,不是更全的扫描器"。四组实验之后,这句话有了四个可引用的支点:
误报最低、attribution 最高、独有的 5 个全是结构化检查、tripwire 在真实数据上工作。
**放弃这个定位去追召回,会同时失去精度和唯一性**——cc-audit 已经在"宽"那一端,差集说明它的宽是用 1,066 个良性买的,
我们追不上也不该追。

### 5.2 四条可以走的路,和数据对它们各说了什么

**a. 静态深化(AST / 数据流)** —— `ROADMAP` A.1,唯一还开着的"Now"项。
数据说:**先别,而且需求比上周更弱**。良性池最大的噪音源(`EXFIL-001` 71)是裸 URL 字面量,issue 016 指向"动词 / 目的地",
不是语法树;漏检分层里归 AST 的 31 个全是 Cisco 服务器源码,定位之外;编码那 16 个用"还原后再扫"就够,不需要数据流。
AST 与"单静态二进制、三个依赖"直接冲突。**第 4 步之后再看逐规则统计**,`plan` 原来的顺序,数据没有推翻它。

**b. 判官作为第二层** —— 数据说:**这是召回唯一真正的增量来源**(42% → 78%),代价可控(+0.4%),
而且逐规则的数说明它的主力规则(LLM-003 / LLM-001)在良性上零升级——它抓的是意图,不是关键词。
形态必须守住三条:只能升级不能降级(`min()` 结构,四家里唯一)、delta 单报不合并、默认关。
下一步不是"让判官进闸门",是**让判官的数字变成带区间的数**(方差 + 全量良性),外加把证据落地那道门也量一次
(skill-safety-bench 上丢了 5 个)。成本是真问题:全量两天半,意味着它只能是 `scan` 时手动开的东西,永远不是 `check` 的一部分。

**c. 覆盖面** —— 两家竞品各自暴露了"面"的问题:cc-audit 读一切但分不清读没读;skill-scanner 只读 skills 且把四个面的零当干净。
我们是 1 个 harness 六个面全读,这是当前的真实优势;`direction` 阶段 3 的 config-layer 扩张(`.cursor` / `.codex` / `.gemini`)
是它的自然延伸——**前提是每个新平台都过同一份语料**。不要做 artifact-layer 广度:那是"广度竞赛在算术上就输"。

**d. 把测量台当产品的一部分** —— 公开语料 + 三列可复算的数 + 逐样本差集,是三家里只有我们有的东西
(Cisco 公开了 P/R 但是手写散文;cc-audit 零;我们的每一列都能 `cmp`,差集能逐样本对号)。M1.6"发数字"的条件
(`plan` §3.1 第 2 步做完)现在离得很近。发的时候:两个分母、按来源、带 n、判官分列、provisional 标清——规矩已经全部写在文件里。

### 5.3 一条必须诚实说的能力缺失

MCP 协议里没有静态工具清单:`tools/list` 是运行时 RPC。首次见到的 stdio MCP server,不执行就无法检查工具描述投毒。
cc-audit 和 skill-scanner 在这一点上同样盲。措辞:"我们不执行,所以对 stdio MCP server 的
工具描述是盲的;这是权衡,不是掩饰"。

### 5.4 不该做的,数据没有改变

规则数竞赛、运行时监控、合规声明、平台广度冲刺、加载期门禁默认开(误报 4.6% 时人会无脑点同意)。
`direction` §4 那张表一条都不用动。
